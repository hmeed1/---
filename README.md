# حضور — مدرسة الهداية الخليفية الثانوية للبنين

تطبيق حضور عربي ثابت يستخدم Supabase للمصادقة وحفظ سجل الحضور سحابيًا. بعد زر **بدء**، يسجل الموظف الدخول ببريده وكلمة مروره ثم يختار الكشف؛ ويسجل الطالب الدخول برقمه الأكاديمي وكلمة مروره لمشاهدة سجله فقط. حساب الطالب الجديد لا يحصل على الصلاحية إلا بعد مراجعة إدارة المدرسة والموافقة عليه.

تدعم الواجهة العربية والإنجليزية، وتتيح للموظف اختيار الصف والشعبة وتسجيل الحضور لكل حصة. يظل نموذج الطباعة بالعربية للمحافظة على تنسيق الكشف المدرسي.

## إعداد Supabase

1. أنشئ مشروعًا في [Supabase](https://supabase.com/dashboard). في `supabase-config.js` ضع عنوان المشروع ومفتاح `publishable` أو `anon` فقط. لا تضع `service_role` أو أي مفتاح سري في ملفات الموقع.
2. لمشروع قاعدة بيانات جديد، شغّل `supabase-schema.sql` في **SQL Editor**. إذا كنت تستعيد كشفًا خاصًا من ملفات النسخ الاحتياطية الموجودة لديك، راجعها وتحقق من صحتها قبل تشغيلها؛ نفّذ `supabase-private-roster.sql` و`supabase-private-migration.sql` مرة واحدة فقط عند الحاجة. هذان الملفان يحتويان بيانات طلاب خاصة، ويجب عدم رفعهما إلى مستودع أو استضافة عامة.
3. شغّل `supabase-auth-migration.sql` بعد إنشاء الجداول المطلوبة. هذا الترحيل يزيل سياسات الوصول العام، ويمنع الزوار غير المسجلين من قراءة السجل أو تغييره، ويقصر بيانات الطالب على سجله. **لا تشغّل `supabase-public-access.sql` بعده**؛ فهذا الملف يعيد فتح الوصول العام.
4. في إعدادات **Authentication** اترك تسجيل المستخدمين مفعّلًا للطلاب، وعطّل تأكيد البريد الإلكتروني. تسجيل الطلاب يستخدم عنوانًا اصطناعيًا مشتقًا من الرقم الأكاديمي، لذلك لا يمكن استلام رسائل التأكيد عليه. لا تعطّل التسجيل الذاتي إلا إذا قررت المدرسة تفعيل حسابات الطلاب بطريقة أخرى.
5. أنشئ حساب الموظف من **Authentication → Users**، ثم غيّر دوره يدويًا إلى `staff` وفعّله في SQL Editor بعد التحقق من الحساب:

   ```sql
   update public.attendance_user_profiles
   set role = 'staff', approved = true
   where user_id = (
     select id from auth.users where email = 'staff@example.com'
   );
   ```

   استبدل البريد التجريبي ببريد الموظف. سجّل الطالب طلبًا من شاشة الدخول، ثم طابق هويته ورقمه الأكاديمي مع سجلات المدرسة قبل الموافقة عليه. لا تعتمد على الرقم الذي أدخله الطالب وحده:

   ```sql
   update public.attendance_user_profiles
   set role = 'student',
       academic_number = public.normalize_academic_number('ACADEMIC_NUMBER'),
       approved = true
   where user_id = (
     select id from auth.users
     where email = 'academic.ACADEMIC_NUMBER@accounts.school.invalid'
   );
   ```

   استبدل `ACADEMIC_NUMBER` بالرقم الأكاديمي الذي تم التحقق منه. حساب غير الموافق عليه يبقى معلّقًا ولا يستطيع قراءة بيانات الحضور.

6. قبل استخدام بيانات حقيقية أو نشر الموقع، اختبر أن الزائر غير المسجل لا يستطيع قراءة `attendance_state` أو `attendance_roster_backup`، وأن حساب الطالب يرى سجله وحده، وأن الموظف الموافق عليه يستطيع إدارة السجل.

## النشر

يمكن نشر ملفات الواجهة الثابتة على Vercel أو استضافة ثابتة أخرى. لا يحتاج الموقع إلى أمر بناء أو اعتماديات. لا تنشر ملفات النسخ الخاصة `supabase-private-roster.sql` و`supabase-private-migration.sql`؛ فهي مستثناة من إعدادات Git وVercel المحلية، لكن تحقّق من ذلك أيضًا عند الرفع اليدوي.

الملف `demo-roster.js` لا يحتوي على كشف طلاب؛ يجب إضافة البيانات الحقيقية إلى قاعدة Supabase الخاصة، لا إلى ملفات JavaScript العامة.
